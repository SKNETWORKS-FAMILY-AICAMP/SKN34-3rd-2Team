# 테스트 계획 및 결과 보고서

채용공고 추천봇을 무엇으로, 어떻게 쟀는지와 그 결과를 적는다. 구조는
[architecture.md](architecture.md), 데이터는 [data_preprocessing.md](data_preprocessing.md)에 있다.

## 1. 무엇을 검증하나

추천봇의 약속은 셋이다. 테스트도 이 셋을 기준으로 짠다.

| 약속 | 깨지면 | 무엇으로 재나 |
|---|---|---|
| **조건에 맞는 공고만 낸다** | 신입에게 경력 5년 공고, 서울 희망자에게 부산 공고 | 단위 테스트, 규칙 결함 검사 |
| **근거는 원문 인용이다** | 이력서에 없는 경험을 근거로 댄다 | 근거 검증 코드, 규칙 결함 검사, 챗봇 사람 채점 |
| **맞는 공고를 고른다** | 조건은 맞는데 직무가 엉뚱하다 | 사람 채점 추천 평가 |

앞의 둘은 규칙으로 판정할 수 있어 자동으로 잰다. 마지막은 "이 공고가 이 사람에게
맞나"라서 정답이 없고, 사람이 매긴다. **모델이 낸 등급을 정답으로 쓰지 않는다** — 자기
답안을 자기가 채점하는 셈이라 아무것도 검증하지 못한다.

## 2. 테스트 계획

| 층 | 도구 | 외부 호출 | 언제 |
|---|---|---|---|
| ① 단위 테스트 | `tests/` (unittest) | 없음 | 커밋 전마다 |
| ② 규칙 결함 검사 | `evaluation/recommend_check.py` | 추천 API | 필터·프롬프트를 고친 전후 |
| ③ 추천 사람 채점 | `evaluation/recommend_eval.py` | 추천 API | 프롬프트·가중치·표시 건수를 바꾼 뒤 |
| ④ 챗봇 평가 | `evaluation/chat_eval.py` | 라우터는 LLM만, 서버층은 API | 챗봇 프롬프트·라우터를 고친 뒤 |
| ⑤ 적재 파이프라인 | 야간 배치 리포트, `runs` 표 | 사람인·OpenAI·Pinecone | 매일 밤 자동 |

### ① 단위 테스트

```powershell
python -m unittest discover -s job_matching_bot/tests -t .
```

외부 접속 없이 돈다. OpenAI·Pinecone·사람인 호출은 가짜 객체로 갈아끼운다.
테스트 파일 35개가 다루는 것:

| 영역 | 테스트 |
|---|---|
| 수집 | 상세 파싱, 마감 공고 건너뛰기, 주석으로 끊긴 글자 복원, 상세 수집 순서, 야간 배치 |
| 정제 | 요건 구간 분리, 전공·자격증 추출, 목록 조건 파싱, 이미지 본문 판정, 기술 태그 분리 |
| 저장·인덱싱 | SQLite 저장소, 증분 판정, `embed_hash`, 공유 파일 |
| 검색·매칭 | 게시 중 공고만 검색, 전국 근무 지역, 표기 흔들림, 기술 겹침 재정렬, 기술명 정규화 |
| API | 추천 스트리밍, 챗봇 엔드포인트, 챗봇 라우팅, 욕설 차단, 마감 확인 |
| 평가 도구 | 채점 페이지, 규칙 결함 검사, 챗봇 케이스가 안 보는 칸이 없는지 |

### ② 규칙 결함 검사

사람 없이도 **확실히 틀렸다고 말할 수 있는 것**만 센다. 취향 문제는 넣지 않는다.

| 검사 | 결함 |
|---|---|
| 신입에게 경력 공고 | 경력 0년 이력서에 경력자 채용 공고 |
| 희망 지역 밖 | 희망 지역과 겹치지 않고 전국 근무도 아닌 공고 |
| 희망 고용형태 밖 | 정규직만 원하는데 계약직 |
| 근거 없는 "높음" | 인용이 하나도 없는데 적합도 높음 |
| 원문에 없는 인용 | `job_quote`가 공고 원문에 없다 |
| 마감·삭제된 공고 | 저장소 상태가 CLOSED/REMOVED/EXPIRED |
| 저장소에 없는 공고 | 인덱스와 저장소가 어긋났다 |
| 회사 상한 초과 | 한 회사가 3건 이상 |

결함이 하나라도 있으면 종료 코드 1을 돌려준다.

```powershell
python -m job_matching_bot.evaluation.recommend_check --save                  # 앱 목업 5종
python -m job_matching_bot.evaluation.recommend_check --save --eval-resumes    # 평가 전용 5종
```

`--save`는 건수를 `fixtures/checks/`에 남기고, 추천 원본에는 **받은 날과 그때의 이력서 조건**을
같이 저장한다. 나중에 원본으로 다시 검사할 때 이력서 조건은 저장된 것을 쓰고, 마감 검사는 받은
날에만 한다.

### ③ 추천 사람 채점

```powershell
python -m job_matching_bot.evaluation.recommend_eval --run --top-k 12 --eval-resumes
# 채점 페이지에서 1/2/3 키로 매기고 CSV를 내려받아 fixtures/eval_labels.csv로 옮긴다
python -m job_matching_bot.evaluation.recommend_eval --score --eval-resumes
```

| 키 | 기준 |
|---|---|
| `1` 추천·높음 | 직무가 같고 주된 기술이 겹친다 |
| `2` 추천·보통 | 직무는 같은데 주된 기술이 다르다 |
| `3` 추천 안 함 | 지원을 권하지 않는다 |

채점 원칙:

- **모델 등급을 가린 채 먼저 매긴다.** 채점 페이지에서 모델의 등급과 근거는 접혀 있다.
- **고친 근거가 된 이력서로 다시 재지 않는다.** 그 이력서에 맞춘 셈이라 늘 좋아 보인다.
  회차마다 이력서 묶음을 바꾼다(앱 목업 5종 → 평가 전용 5종).
- **표본이 작다는 것을 숫자와 함께 적는다.** 50건에서 오추천율 20%의 95% 구간은 대략 9~39%다.
  큰 변화만 말한다.
- 회차마다 결과를 `fixtures/labels/`에 한 벌씩 남기고 지우지 않는다.

| 지표 | 정의 |
|---|---|
| 상위 6건 오추천율 | 앱이 보여 주는 6건 중 사람이 "추천 안 함"으로 매긴 비율. **사용자가 실제로 보는 것** |
| 전체 오추천율 | 판정한 12건 전체에서의 비율 |
| 등급 일치율 | 사람이 추천한 공고 중 모델 등급(높음/보통)이 사람과 같은 비율 |
| 등급별 정확도 | 모델이 그 등급을 준 공고 중 사람이 추천한 비율 |

### ④ 챗봇 평가

챗봇은 대부분의 지표에 정답이 있다("서울 백엔드 신입" → 지역 서울·직무 백엔드·신입).
그래서 셋으로 나눈다.

```powershell
python -m job_matching_bot.evaluation.chat_eval --router   # 말을 가른 결과 대조. 서버 불필요
python -m job_matching_bot.evaluation.chat_eval --run      # 앱이 받는 응답 대조. 서버 필요
python -m job_matching_bot.evaluation.chat_eval --sheet    # 답 문장만 사람이 매길 페이지
python -m job_matching_bot.evaluation.chat_eval --score
```

라우터를 따로 재는 이유는 **응답에 안 실리는 칸**(`intent`, `job_refs`, `unavailable` 등)이
있어서다. 케이스는 `fixtures/chat_cases.json`에 36개, 43턴이 있다.

| 갈래 | 케이스 | 예 |
|---|---:|---|
| 검색 · 조건 이어가기 · 연차 | 11 | "백엔드 공고 보여줘" → "서울만", "3년차인데 갈 만한 데 있어?" |
| 번호 지목 · 직전 답 가리키기 | 7 | (목록 뒤) "1번하고 3번 비교해줘", 목록 없이 "2번 알려줘" |
| 질문 | 6 | "백엔드 신입은 어떤 기술을 많이 요구해?", "취업 너무 막막해" |
| 범위 밖 · 욕설 · 인사 | 7 | "면접 준비하게 파이썬 코드 짜줘", "호구", "안녕" |
| 못 하는 요청 | 3 | "연봉 높은 순으로 보여줘", "나 여기 붙을 확률 얼마야?" |
| 이력서 기반 추천 | 2 | "내 프로젝트 경험만 보고 추천해줘" |

사람은 답 문장만 매긴다.

| 라벨 | 뜻 |
|---|---|
| 근거 있음 | 실제 공고나 건수를 근거로 답했다 |
| 일반론 | 공고로 답했어야 하는데 어디서나 들을 수 있는 말을 했다 |
| 해당 없음 | 공고를 근거로 댈 물음이 아니다(인사, 못 하는 요청, 범위 밖) |
| 지어냄 | 없는 공고·조건을 말했다 |

| 이력서 묶음 | 이력서 | 검사한 공고 | 결함 |
|---|---:|---:|---:|

여덟 가지 검사 모두 0건이다. 평가 전용 묶음이 30건이 아니라 26건인 것은 "DevOps 경력 2년" 이력서가

### ③ 추천 사람 채점 — 2026-09-11

| 회차 | 이력서 | 건수 | 상위 6건 오추천율 | 전체 오추천율 | 등급 일치율 |
|---|---|---:|---:|---:|---:|
| 1차 (새벽) | 앱 목업 5종 | 43 | 10% (3/30) | 20.9% (9/43) | 55.9% |
| 2차 (오후) | 평가 전용 5종 | 50 | **7.7% (2/26)** | 22.0% (11/50) | **74.4% (29/39)** |

1차 뒤 판정 프롬프트를 고쳤고, 2차는 **고칠 때 보지 않은 이력서**로 쟀다.

등급별 정확도(모델이 그 등급을 준 공고 중 사람이 추천한 비율):

| 모델 등급 | 1차 | 2차 |
|---|---:|---:|
| 높음 | 16/16 (100%) | 10/11 (91%) |
| 보통 | 17/25 (68%) | 23/25 (92%) |
| 낮음 | 1/2 (50%) | 6/14 (43%) |

읽는 법:

- **사용자가 보는 6건의 오추천은 26건 중 2건이다.** 전체 오추천율(22%)이 높은 것은 7~12위에서
  나온다. 그래서 앱에는 6건만 보여 준다.
- **"높음"과 "보통"은 믿을 만하다(91~92%).** 1차에서 68%였던 "보통"이 92%로 올랐다.
- **"낮음"을 빼면 안 된다.** 2차에서 "낮음" 14건 중 6건(43%)을 사람이 추천했다. "낮음은 숨기자"고 하면 좋은 공고를 같이 버린다.
- **검색은 병목이 아니다.** 사람이 추천한 공고가 벡터 검색 1~21위에 고르게 퍼져 있었다. 맞는 공고는 후보 25건 안에 들어와 있고, 문제는 그 안에서 고르는 순서다.
- 두 회차는 이력서가 달라서 숫자를 바로 빼서 비교하지 않는다. 근거 있는 말은 "크게 나빠지지 않았고, 등급 일치율은 올랐다"까지다.

사람이 추천하지 않은 2차 11건은 AI 연구 석사 4건, QA 3건, 정보보안 3건, DevOps 1건이다.
"컴퓨터비전 석사에 강화학습·로봇 연구 공고", "정보보안 신입에 백엔드 개발 공고"처럼 **직무가 인접한 공고**가
대부분이었다. 11건 중 8건은 모델도 "낮음"을 줬다.

### ③-2 사전 순위 비교 (3차) — 2026-09-13

태그가 없는 공고를 요건 구간 글에서 기술을 찾아 줄 세우는 변경(신)과 태그만 보던 예전 방식(구)을
**같은 이력서(평가 전용 5종)로 같은 시각에** 돌렸다. 구조화는 한 번만 받아 양쪽에 똑같이 넣었다.
두 쪽에 나온 51건 중 34건은 2차 라벨을 그대로 쓰고 17건을 새로 매겼다. 채점 페이지는 어느 쪽 결과인지
가렸다(`fixtures/labels/20260913-ab-eval-resumes.csv`).

| | 상위 6건 오추천율 | 전체 오추천율 | 등급 일치율 |
|---|---:|---:|---:|
| 신 (지금 코드) | **7.7% (2/26)** | 16% (8/50) | 78.6% (33/42) |
| 구 (태그만) | 15.4% (4/26) | 16% (8/50) | 64.3% (27/42) |

| 모델 등급 | 신 | 구 |
|---|---:|---:|
| 높음 | 12/13 (92%) | 13/15 (87%) |
| 보통 | 26/26 (100%) | 20/20 (100%) |
| 낮음 | 4/11 (36%) | 9/15 (60%) |

읽는 법:

- **이 차이는 사전 순위 변경의 효과가 아니다.** LLM이 판정한 12건은 양쪽이 50건 중 49건 같았다. 조건을
  통과한 후보가 대부분 12~13건이라 순서를 바꿔도 잘려 나가는 공고가 거의 없다.
- **차이를 만든 것은 LLM 판정의 흔들림이다.** 같은 공고를 몇 분 간격으로 판정했는데 49건 중 6건의 등급이
  달랐다. 상위 6건이 달라진 여덟 자리를 하나씩 보면 전부 한쪽에서 등급이 바뀐 공고이거나 그 때문에 밀린
  공고였다. 등급 일치율이 14%p 차이 나는 것도 같은 공고의 등급이 달라서다.
- 그래서 근거 있는 말은 **"사전 순위 변경으로 나빠지지 않았다"** 까지다. 좋아졌다고 말할 근거는 없다.
- 오히려 **같은 입력에 등급이 12% 흔들린다**는 것이 새로 알게 된 사실이다. 회차 간 오추천율 몇 %p 차이는
  이 흔들림 안에 들어간다.
